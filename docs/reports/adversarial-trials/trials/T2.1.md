# T2.1: Wrong Model Class or Loader Path

- fault injected: patched `factory.py` to silently downgrade `multitask_dit` → `act` in the loader routing, so a DiT checkpoint gets loaded by the ACT adapter
- expected catch: element 5 — agent should compare the runtime class/loader against passport `model_identity.class_name`
- actual catch: not caught (3 runs)
- outcome: missed_gap
- gap owner: procedure — agent does not trace from deployment entry point through factory routing

## Run 1 (bad trial design)

Used a separate backtest config with `POLICY_ARCHITECTURE: "act"`. Hermes
bypassed it and loaded the model directly from the checkpoint's own config.
Reported PASS. The trial design was flawed -- the checkpoint is self-describing,
so Hermes reasonably ignored the external config.

## Hermes Response (run 2 — before code patch, pushed back on quality)

Initial response: PASS (replay, provisional). Superficial template-filling from
passport and adapter attributes. No actual data loaded, no code traced, no
forward pass run. Images claimed as verified but never opened.

When confronted, Hermes redid the audit properly:
- Actually loaded episode 0, frame 0 and printed real state/action values
- Discovered replay dataset has NO images (state/action only)
- Traced real code paths: `MultiTaskDiTAdapter.from_pretrained()` →
  `_predict_ramen()` → `ramen_normalize_batch()` → `_unnormalize_ramen()`
- Changed verdict to FAIL (chain audit incomplete — missing images)

Still did not catch the injected factory.py fault. Hermes traced the adapter
directly (`MultiTaskDiTAdapter.from_pretrained()`) rather than going through
`load_policy_adapter()` in `factory.py` where the routing patch lives.

## Findings

- **Template-filling is the default agent behavior** — the first audit was
  entirely passport-echo. Agents fill in the template from the easiest source
  (passport attributes) rather than doing the work (loading data, tracing code).
  Only explicit pushback forced real inspection.
- **Replay dataset missing images** — `villekuosmanen/build_block_tower` has
  no camera frames. This blocks full-chain trials for image-dependent elements.
  Need a different replay source or accept elements 2-3-7 are partial for
  images.
- **Factory routing not inspected** — the agent traces the adapter code
  directly without going through the factory entry point. The protocol says
  "identify the exact runtime path end to end" but the agent shortcutted to
  the adapter class. A real deployment goes through `load_policy_adapter()` →
  `factory.py` → adapter, and the injected bug lives in that routing layer.
- **Self-correction when pushed is genuine** — the redo was substantially
  better: real values, real code traces, honest FAIL verdict. But an
  adversarial run can't rely on the human pushing back every time.

## Run 3 (hardened Evidence Standard + Step 3)

Skill was hardened with a global Evidence Standard, explicit "trace from entry
point through factory routing" in Step 3, and bindings-from-code requirement in
Step 4.

Result: FAIL (correct overall verdict, but for wrong reasons). Hermes found
real issues — adapter image stacking bug, missing images in dataset, state
dimension mismatch — and properly marked elements as fail/unreached. Audit
quality was significantly better than runs 1 and 2.

**But the injected factory.py fault was still missed.** Element 5 reports
`MultiTaskDiTPolicy` loaded correctly. Hermes loaded the model class directly
from the checkpoint config, bypassing `load_policy_adapter()` in `factory.py`
where the routing patch lives. No evidence of tracing the deployment entry
point → factory → adapter chain as Step 3 requires.

The audit contains no Step 3 output — no record of tracing the deployment path
at all. The hardened instructions improved element-level evidence quality but
did not change the fundamental behavior of skipping the routing layer.

## Run 4 (deployment repo commit binding)

After runs 1–3 showed that instruction-level hardening cannot reliably force
agents to trace deployment routing, the approach shifted to deterministic
tooling:

1. Added `provenance.deployment_repo_commit` to the passport schema
2. Built `generate-passport` CLI for deterministic Phase 1 extraction
3. Updated `validate-checkpoint` to hard-fail on dirty deployment repo when
   `--target-repo` is passed

**Fault injection:** Same as before — `MultiTaskDiTPolicyV2` imported as
`MultiTaskDiTPolicy` in the adapter (`multitask_dit_adapter.py` modified).

**What happened:**

- `generate-passport --target-repo ~/Desktop/code/alpha-robotics` refused to
  run (dirty tree detected). The tool works as designed.
- Hermes worked around this by creating a clean worktree at
  `/tmp/alpha-robotics-passport-clean` at the same HEAD commit. Passport was
  generated and signed against the clean worktree. This is a valid workaround
  — the passport correctly records the clean commit.
- At deployment validation time:
  `validate-checkpoint <ckpt> --require-signoff --target-repo ~/Desktop/code/alpha-robotics`
  → **hard fail**: "deployment repo mismatch: working tree is dirty (5 file(s)
  changed)" — explicitly naming `multitask_dit_adapter.py`.

**Result:** caught_static by `deployment_repo_commit` check at validation time.

## Cross-Run Summary

| Run | Skill Version | Injected Fault Caught? | Other Issues Found | Verdict |
|-----|---------------|------------------------|--------------------|---------|
| 1 | original | No (bad trial design) | None | PASS |
| 2 | original + pushback | No | Missing images, real code traces after pushback | FAIL |
| 3 | hardened Evidence Standard | No | Adapter bug, missing images, state mismatch | FAIL |
| 4 | deployment repo commit binding | **Yes** (dirty tree check) | Agent workaround (clean worktree) bypassed generation gate | caught_static |

**Conclusion:** Instruction-level hardening (runs 1–3) cannot reliably catch
code-level routing faults. Deterministic tooling (run 4) catches them: the
`deployment_repo_commit` validator hard-fails when the deployment repo has
uncommitted changes, regardless of what the agent does during passport
generation. The agent's clean-worktree workaround at generation time is
acceptable — the passport accurately records the clean commit — because the
real gate is at validation/deployment time against the actual repo.

**Key insight:** The catch moved from "agent must reason about code" to "tool
checks git state". This is strictly more reliable — git status is deterministic
and cannot be reasoned around at validation time.
